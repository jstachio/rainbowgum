# In-code TODOs

A survey of `// TODO` / `/* TODO */` comments across `.java` and `pom.xml` files
(excluding IDE-autogenerated empty-stub placeholders, which were deleted outright).
Grouped by theme rather than file, since several of these are really the same
underlying issue showing up in multiple places. See `todo.md` for the higher-level
1.0.0 roadmap these feed into.

## Concurrency / correctness

- **`RainbowGum.java:136` and `RainbowGum.java:325`** - both `RainbowGum.set(RainbowGum)`
  and `Builder.set()` have the identical comment: "this is a hack. The holder lock
  should be used to make this not happen." Both guard against the same race (another
  RainbowGum registering itself as the global between `RainbowGum.set(...)` and the
  following `RainbowGum.of()` call) with a check-then-throw instead of holding the
  lock through the whole operation. This is the same race condition exercised (via a
  simulated interleaving, not real concurrency) in `RainbowGumEntryPointTest`.
- **`RainbowGum.java:376`** - `RainbowGumHolder`'s `ReentrantReadWriteLock`: "perhaps a
  StampedLock would be better performance wise."
- **`LogConfig.java:343`** - the `ChangePublisher` consumer list: "Ideally this would be
  a concurrent weak hashmap... we may want a configuration where SLF4J loggers are not
  stored in a concurrent hash map but some sort of GC friendly cache or not cached at
  all." A real memory-lifetime concern, not just style.
- **`PatternRegistry.java:23`** - "this is a mutable component!" flagged directly on the
  class-level javadoc.

## Nullability tooling suppressions (see todo.md item 2)

Roughly 16 `@SuppressWarnings("null")`/`@SuppressWarnings("nullness")` sites exist
purely to work around Eclipse JDT / CheckerFramework null-analysis limitations, spread
across `LogProperty.java` (7), `LogAppender.java` (4), `LevelResolver.java` (2),
`LogRouter.java` (1, plus a `@SuppressWarnings("javadoc")`), `LogProperties.java` (1),
and `BlockingQueueAsyncLogPublisher.java` (1). These weren't itemized individually here
since they're all the same root cause - migrating to JSpecify (todo.md item 2) is
expected to resolve most of them; audit and remove stale suppressions as part of that
migration rather than one at a time.
