# Rainbow Gum 0.11.0

This release's headline is **observability for the logging system itself**: a new
Alerts/Metrics subsystem tells you when Rainbow Gum's own machinery is having problems
(a dropped event, a failed appender write), with a Spring Boot Actuator/Micrometer
bridge to get those counters into your existing metrics backend with zero config.
Alongside that: built-in log file rolling (no external tool required for the common
case), a new zero-config bundle for tests and simple apps, and finer control over
`ThreadLocal` usage for applications that want none anywhere in the logging path.

## New: Alerts and Metrics

Two small, separate APIs off `LogConfig` report on Rainbow Gum's own health, as opposed
to the application events flowing through the normal `LogRouter`:

- `LogAlerts` - discrete problems (an appender failing to write, an async publisher's
  queue overflowing) kept in a small in-memory ring buffer and reported immediately
  (currently to stderr). Subscribe with `LogAlerts#addListener(...)` to bridge alerts to
  whatever paging/alerting system your application already has.
- `LogMetrics` - cheap, high-frequency counters (events dropped, events failed, an
  encoder buffer having to self-shrink) that would be wasteful to record as discrete
  alert events. `LogMetrics.StandardMetric` enumerates the fixed, well-known set.

Both are configurable (`logging.alerts.capacity`, `logging.alerts.unobservedErrorsAction`)
and, like everything else in Rainbow Gum, have no required dependency on the other - a
future Micrometer-backed `LogMetrics` doesn't need to touch how alerts are recorded.

### New module: `rainbowgum-spring-boot4-actuator`

Bridges every `LogMetrics.StandardMetric` to Micrometer as a `rainbowgum.<name>`
counter, tagged by level. Activates automatically - no properties, no bean to register -
as soon as Micrometer is on the classpath (i.e. as soon as your app already depends on
Spring Boot 4's `spring-boot-starter-micrometer-metrics`). Deliberately its own module
rather than bundled into the starter, since pulling in Micrometer is an opt-in choice,
not something every Rainbow Gum + Spring Boot user should get by default. Boot 4 only
for now; no Boot 3 equivalent yet.

## New: built-in rolling file output

The `rainbowgum-file` module (renamed and expanded from `rainbowgum-rolling`) now
provides size-based rolling under a new `rolling://` URI scheme, alongside the existing
plain (non-rolling) `file://` output:

```properties
logging.appenders=myapp
logging.appender.myapp.output=rolling:///var/log/app.log?maxFileSize=10485760&maxHistory=7
```

This is deliberately basic - just enough to keep a small/desktop app's disk from
filling up, not a substitute for a real log rotation/aggregation policy. There's no
calendar-based rotation, no independent compression schedule, and no coordination
across multiple processes writing the same file. For anything beyond that, the
existing `logrotate`-based external-tool approach (unchanged, still documented) remains
the recommended path and doesn't depend on this module at all.

## New: `rainbowgum-simple` / `rainbowgum-simple-props`

A zero-configuration bundle for unit-testing a library module or a very simple
application - drop it on the test classpath and logging just works, no setup required.
Comparable to `slf4j-simple`, but also brings `java.lang.System.Logger` support (which
`slf4j-simple` doesn't). Drop a `logging.properties` file on the classpath to customize
it; resolution order is System properties, then `RAINBOWGUM_`-prefixed environment
variables, then that file. Ships a GraalVM native-image resource-config out of the box.
Good for testing, simple applications, or older applications that prefer letting the
logging system handle loading its own configuration - for finer control or dynamic
configuration, use a real `PropertiesProvider` or the programmatic builders instead.

## Finer control over `ThreadLocal` usage

For applications that want a hard guarantee of no `ThreadLocal` anywhere in the logging
path (some virtual-thread-heavy or GraalVM native workloads care about this):

- New `LogAppender.AppenderType` enum (split out of the old appender flags) - the new
  `LOCK_NEW_BUFFER` type allocates a fresh buffer per event instead of reusing a
  per-thread one, trading that allocation for the `ThreadLocal`-free guarantee.
- `logging.mdc.type=NOOP` disables MDC entirely (renamed from the old
  `logging.mdc=ENABLED/DISABLED`, see Breaking Changes below).
- New `logging.global.threadlocalDisabled=true` is the one-flag version of both:
  process-wide, forces every appender off `ThreadLocal`-backed buffering and disables
  MDC if the SLF4J module is in use.

## More accurate SLF4J caller info

The SLF4J facade now implements `LoggingEventAware` and, conditionally,
`LocationAwareLogger` for caller-info-enabled loggers, so the calling
class/method/line Rainbow Gum reports is resolved the way SLF4J itself expects rather
than an approximation. Caller info also moved to its own independent property,
`logging.caller.<name>` (see Breaking Changes) - it no longer has to ride along with
level-changing.

## For library/plugin authors

Nullability annotations moved from Eclipse JDT (`org.eclipse.jdt.annotation`) to
[JSpecify](https://jspecify.dev/) (`org.jspecify.annotations`) throughout every public
API. If your own build runs a null-checker (CheckerFramework, NullAway, etc.) against
Rainbow Gum's annotations, point it at JSpecify instead - CheckerFramework's Nullness
Checker already understands JSpecify natively with no configuration change.

## Breaking changes

- `logging.mdc=ENABLED/DISABLED` is now `logging.mdc.type=THREAD_LOCAL/NOOP`.
- `logging.change.<name>=caller` no longer exists - caller info is now
  `logging.caller.<name>=true` (or a `CallerType` name), resolved completely
  independently of `logging.change.<name>`'s level-changing permission.
