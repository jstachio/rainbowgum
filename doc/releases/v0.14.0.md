# Rainbow Gum 0.14.0

This release is effectively **1.0.0-RC3**. The headline is **MDC-like context for every
logging API**: JUL, `System.Logger`, JBoss Logging, and Log4j2 events now carry the same
request context as SLF4J events, from whichever context store the application already
uses. Alongside that: a new default async publisher, profile-based configuration for
`rainbowgum-simple-props`, bootstrap debug modes, Helidon SE 27 support, and a set of
safety fixes such as credential redaction in diagnostics. Several APIs changed on the way
to 1.0; see [Breaking changes](#breaking-changes).

## New: key values for every logging API

Previously only SLF4J events picked up MDC. JUL and `System.Logger` have no context API of
their own, so their events carried none, even when the application had set SLF4J's MDC or
Log4j's `ThreadContext`. Each context store now registers itself as a
`LogEventFactory.KeyValuesContributor`, and every logging API merges the registered
contributors into its events:

- `rainbowgum-slf4j` contributes SLF4J's MDC.
- `rainbowgum-jboss-logging` contributes JBoss Logging's MDC.
- `rainbowgum-log4j2` contributes Log4j's `ThreadContext` map.
- `rainbowgum-scopedkeyvalues` contributes scoped key values, and no longer requires
  `rainbowgum-slf4j`.

There is nothing to configure: having the module on the classpath is enough. A facade's own
store wins over the others for its own events, so SLF4J events still prefer MDC values.
Contributors are identified by the sealed `KeyValuesContributor.Source` enum, so an unknown
library cannot inject key values into every event.

Applications can register their own contributor under `Source.Standard.USER`, which wins
over every other source. It is reserved for applications, not libraries:

```java
KeyValuesContributor.register(config.serviceRegistry(), Source.Standard.USER, () -> myContext());
```

### Clearing per thread state

For thread pools, two calls remove everything Rainbow Gum or a context store keeps on the
current thread:

```java
KeyValuesContributor.global().clear(); // MDC, ThreadContext map and stack, JBoss MDC and NDC
LogAppender.clearThreadLocals();       // per thread encoding buffers of thread local appenders
```

## New: follow option for stdout and stderr

The console outputs cache `System.out` and `System.err` when they are created, so a later
`System.setOut`, for example from a test that captures standard out, missed log output. A
new `stream` parameter selects an output that reads the stream on every write, like
Log4j2's `follow` and Logback's console target
([#163](https://github.com/jstachio/rainbowgum/issues/163)):

```properties
logging.appender.console.output=stdout:///?stream=follow
# or
logging.output.console.stream=follow
```

`cached` stays the default, since following loops if standard out is redirected into
logging. Programmatically, use `StdOutOutputBuilder` or `StdErrOutputBuilder` with
`ConsoleStream`.

## New default async publisher

`BatchSwapAsyncLogPublisher` (in `io.jstach.rainbowgum.publisher`, now an exported package)
is the new default for the `async` publisher. Producers fill one bounded batch while the
worker writes the previous one, events keep insertion order, and rejected events are
counted in `events.dropped` with one alert per rejection reason. Shutdown no longer
interrupts the worker in the middle of output I/O: `close()` stops intake, lets producers
that were already admitted finish, and waits up to `logging.publisher.<name>.shutdownTimeout`
(default 10 seconds) for queued events to be written.

Select it explicitly with the `batchswap` scheme to keep it if the default changes later.
Queue depth is reported through a new `events.queued` gauge.

## `rainbowgum-simple-props`: profiles and stricter checks

`logging.properties` can now be layered with `logging-<profile>.properties` resources:

```sh
-Dlogging.profiles=local-dev,dev    # or RAINBOWGUM_profiles, or SimpleProperties.builder().profiles(...)
```

The first listed profile has the highest priority, and `logging.properties` is the
fallback for every profile. With no profiles selected, an optional
`logging-default.properties` is loaded. Every selected profile resource other than
`default` must exist, or startup fails.

The module also became stricter:

- It only activates when the base `logging.properties` resource exists.
- Keys in the base resource must start with `logging.`; an unprefixed key now fails
  initialization by default, with its resource and line number. Use
  `logging.simpleprops.strict=alert` to report and continue, or `off` to skip the check.
- The selected profiles and each loaded resource are recorded as informational alerts.

## Bootstrap debug modes

`-Dlogging.debug` prints what happened during initialization:

| Mode | Prints |
| --- | --- |
| `OFF` (default) | nothing |
| `ERROR` | the failure and collected alerts if building `LogConfig` fails |
| `INFO` | also the collected alerts after every successful build |
| `ALL` | also the `LogReporter` report once logging has started |

It is read before properties providers run, so it cannot be set in `logging.properties`.
`true` and `false` are aliases for `ALL` and `OFF`.

## New module: `rainbowgum-helidon27`

Helidon SE 27 support through the same `LoggingProvider` integration as
`rainbowgum-helidon4`. Helidon 27 requires Java 27, so this module is compiled for Java 27.

## File output: data sizes and recovery

- Rolling `maxFileSize` and `totalSizeCap`, and `FileOutput`'s `bufferSize`, accept data
  sizes such as `10MB`, `512 kb`, or `1.5g` (a superset of Logback's format) as well as
  plain byte counts.
- Failed rotation and recovery are reported with a new `roll.fail` metric and file
  specific alerts, and a closed output recovers without truncating surviving data.
  Reopen attempts and failures are also counted.

## Safer diagnostics

- Credentials are redacted from output URIs and URI-valued properties in reports,
  provisioning errors, and property descriptions, including user info and credential
  query parameters.
- Sensitive property key redaction was fixed.
- Configuration error messages list the valid values for enum properties and format long
  property source listings across lines.
- A missing output scheme that belongs to an optional module (now including `jfr`) names
  the module's versioned Maven coordinates and links to its documentation.

## Breaking changes

- **`LogMetrics`:** `counters()` and `LogMetrics.Counter` are now `snapshot()` and
  `LogMetrics.Metric`, whose value is `value()`. Gauges were added.
- **`LogAlerts`:** `error(LogEvent)` is now `alert(LogEvent)`. The default alert capacity
  is now 512.
- **`LogConfig` reuse:** a `LogConfig` can back only one `RainbowGum`. A second builder or
  build using the same config throws `IllegalStateException`. It never worked correctly:
  outputs failed to provision and flush or reopen reached the first gum's closed appenders.
- **`rainbowgum-simple-props`:** requires the base `logging.properties` resource and rejects
  unprefixed keys by default (see above).
- **`LogEventFactory.defaultKeyValues()`** now defaults to the registered key values
  contributors instead of empty key values.
- **`rainbowgum-slf4j`:** `RainbowGumSLF4JServiceProvider.SCOPED_KEY_VALUES_SERVICE_NAME`
  is removed, replaced by key values contributors.
- **Rolling metrics** were renamed to match their constants, for example `reopen.fail`.

## Under the hood

- `PropertiesProvider` implementations can keep raising alerts after
  `provideProperties` returns; their alerts are buffered and handed to the real
  `LogAlerts` once it exists.
- Internal failure logging (`MetaLog`) no longer depends on a separate fail-safe appender.
- The Micronaut and Helidon integrations now bring in the runtime logging dependencies
  they need.
- `analyze.sh` fails immediately on unknown profile names.

## Docs

The user guide gained sections on simple properties profiles, bootstrap debugging, and
the console stream option. `why_rainbowgum_is_better.md` was reorganized and now states
that core never reads classpath resources, files, or environment variables on its own.
Release notes now live in `doc/releases`.
